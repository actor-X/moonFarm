# MoonFarm 登录与顶号一致性方案

> 状态：已实施（auth/gate/Database + 并发测试）
> 影响范围：`server/game/auth/Auth.lua`、`server/game/gate/Gate.lua`、`server/game/service_gate.lua`、`server/common/Database.lua`、`tools/test_login_concurrency.js`
> 不涉及：C++ 内核、协议格式、客户端

## 1. 背景与目标

现有登录链路（gate → auth → user）没有会话代次，也没有对同一 uid 的登录做串行化。
单人正常登录没有问题，但"顶号 / 断线重连 / 双开 / 客户端重发登录包"存在时序错乱，
其中一类问题会真正导致存档异常（同一玩家两份内存数据互相覆盖）。

本方案的目标：

1. 同一 uid 的登录、加载、绑定在同一时刻只有一个在执行（单飞）。
2. 旧连接的异步事件（close）永远不会作用到新会话上。
3. 并发首次登录同一个 openid 只会得到同一个 uid、一个 user 服务。
4. 客户端在登录过程中断开时，服务端不会留下"假在线"状态。
5. 不引入新协议、不改客户端、必要时可单独回滚。

## 2. 现状与问题分析

### 2.1 相关代码

| 位置 | 作用 |
| --- | --- |
| `game/service_gate.lua:28-47` `on_message` | 未绑定连接的首包转 auth，已绑定连接的消息转发给 user |
| `game/service_gate.lua:49-61` `on_close` | 连接关闭：清 `fd_map/uid_map`，通知 auth `Disconnect(uid)` |
| `game/gate/Gate.lua:44-61` `Kick` | 按 uid 或 fd 关连接 |
| `game/gate/Gate.lua:63-85` `BindUser` | 把 fd 绑定到 uid，顺带踢掉旧连接 |
| `game/auth/Auth.lua:96-138` `C2SLogin` | openid→uid，顶号判断，调用 `doAuth` |
| `game/auth/Auth.lua:33-93` `doAuth` | 创建/复用 user 服务，`User.Load/Login`，绑定，回包 |
| `game/auth/Auth.lua:179-186` `Disconnect` | 把玩家置为离线并通知 user 服务 `User.Logout` |
| `game/user/User.lua:68-109` | `Login/Logout/Offline`，`Offline` 里立即落盘 |

框架事实（本方案依赖）：

- auth 的每条 `lua` 消息都在独立协程中执行，`User.Load/User.Login`、Redis 查询等 RPC 处会 yield，
  在 yield 期间 auth 可以处理其它消息 —— 即 **auth 内部是并发可重入的**。
- 同一发送者发给同一接收者的消息有序；不同发送者之间没有顺序保证。
- `moon.new_service` 的 `unique` 默认为 `false`（`src/lualib-src/lua_moon.cpp:290`），
  同名服务不会报错，可以并存。
- gate 收到的 fd 由 `server::nextfd()` 分配，**全局单调递增、永不复用**（`src/moon/core/server.cpp:315-332`），
  适合作为会话身份。

### 2.2 问题清单

| # | 问题 | 触发条件 | 后果 |
| --- | --- | --- | --- |
| P0-1 | 顶号时迟到的 `Disconnect` 把新会话置离线 | 旧连接 close 事件晚于新登录的 `User.Login` 到达 auth | user 服务 `state.online=false`，而 gate/auth 认为在线；下线不立即落盘，`Offline` 钩子时序错乱 |
| P0-2 | 并发登录创建两个 user 服务 | `uid_map[uid]` 在 `Load+Login` 完成后才写入，期间有多次 yield | 同一 uid 两份内存数据、各自 5 秒自动存档，last-write-wins，丢更新/回档；孤儿服务关服时不被 `Exit` |
| P1-1 | `BindUser` 返回值被忽略 | 客户端在 auth 完成前断开 | auth 已置 `online=true`、user 已 Online，但永远没有 Logout，形成假在线 |
| P1-2 | `auth_watch` 的 sign 用 `tostring(msg)` | 消息队列槽位地址复用 | "客户端已断开/登录包已被覆盖"的检测不可靠 |
| P1-3 | 新 openid 并发首次登录 | `getuidbyopenid → incr → hset` 三步非原子 | 同一 openid 生成两个 uid，账号数据分裂 |
| P2-1 | 旧连接在途消息 | 顶号后旧 fd 已进 gate 队列的消息 | 因 `fd_map` 已被清空，被当作"登录包"转给 auth |
| P2-2 | 旧会话响应串到新连接 | S2C 按 uid 路由 | 新客户端可能收到旧会话请求的响应（当前协议无请求 id，影响有限） |

### 2.3 两个关键时序（现状）

**P0-1 顶号竞态**

```
client B        gate                     auth                     user
  │ C2SLogin      │                        │                        │
  ├──────────────►├───────────────────────►│ 查 openid/uid          │
  │               │                        │ old.online → Gate.Kick │
  │               │                        │ 发 User.Logout ───────►│
  │               │                        │ User.Login (RPC) ─────►│  (yield)
  │               │ Kick: close(fd_A)      │                        │
  │               │ 旧 fd close 事件       │                        │
  │               ├── Disconnect(uid) ────►│ 再次发 User.Logout ───►│  Login 已先到，
  │               │                        │                        │  Logout 后到 → 离线
  │               │◄── BindUser ───────────┤ Login 返回，置 online  │
  │◄── S2CLogin ──┤                        │                        │
```

最终：gate/auth 认为在线，user 服务实际为离线。

**P0-2 并发建服务**

```
请求 1: uid_map[uid]==nil → new_service(S1) → Load(S1) …… yield
请求 2: uid_map[uid]==nil → new_service(S2) → Load(S2) → Login(S2) → uid_map[uid]=S2
请求 1 返回: Login(S1) → uid_map[uid]=S1（覆盖）
```

两个服务都存在、都会自动存档，且 gate 的绑定与 auth 的 `uid_map` 可能指向不同实例。

## 3. 设计原则

1. **auth 是唯一权威**：登录、顶号、断线对在线状态的影响，全部由 auth 决定。
2. **按 uid 串行**：auth 内为每个 uid 提供一把 FIFO 锁，登录（含 `PullUser`）在锁内完成。
   不同 uid 之间仍然并发。
3. **fd 是会话身份**：`Disconnect/Kick` 都携带 fd；auth 只处理与 `u.fd` 匹配的断线事件，
   过期事件直接丢弃。
4. **先失效、再绑定、后登录**：
   1) auth 侧先把旧会话置为无效（`u.fd=0, u.online=false`）；
   2) gate 原子地"校验新连接 → 踢旧 fd → 绑定新 fd"；
   3) 再调用 `User.Login`（其内部会对旧在线状态执行 `Offline` 钩子）；
   4) 更新 auth 状态并下发 `S2CLogin`。
5. **不额外发 `User.Logout`**：顶号时的下线钩子由 `User.Login` 内部的
   `if state.online then batch_invoke("Offline")`（`User.lua:73-75`）承担，避免同一会话出现
   两条来源不同、顺序不定的 Logout。

## 4. 会话模型

### 4.1 状态

```lua
-- auth
context.uid_map[uid] = {
    addr_user,     -- user 服务地址
    openid,
    name,
    online,        -- 是否存在已绑定连接
    fd,            -- 当前连接 fd；0 表示 auth 侧无有效会话
    logouttime,
}

local uid_locks = {}   -- uid -> { locked = bool, waiters = { co, ... } }
```

不变量：

- `u.online == true` 时 `u.fd ~= 0`；
- 登录临界区内（从 `u.fd=0` 到重新赋值）任何到达的 `Disconnect` 都被 fd 校验丢弃；
- 同一时刻每个 uid 最多一个登录流程持有锁。

### 4.2 目标时序（顶号）

```
client A(旧)      gate                         auth                    user
   │               │                             │                       │
B: │ C2SLogin      │                             │                       │
   ├──────────────►├────────────────────────────►│ openid→uid            │
   │               │                             │ lock(uid)             │
   │               │                             │ u.fd=0; u.online=false│
   │               │◄─ GateRpc.BindUser(fd,sign,uid) ─────────────────────┤
   │               │  校验 auth_watch             │                       │
   │               │  close(fd_A); uid→fd_B      │                       │
   │               ├────────────────────────────►│ ok                    │
   │ A 被踢(close) │                             │ User.Login (RPC) ────►│ Online 钩子
   │               │                             │◄──────────────────────┤
   │               │                             │ u.fd=req.fd; online=true
   │               │◄──────── S2CLogin(uid) ─────┤                       │
   │               │                             │                       │
   │               ├─ Disconnect(uid, fd_A) ────►│ fd 不匹配 → 忽略      │
```

### 4.3 第二个 C2SLogin 到达时会发生什么

锁保证同一 uid 的 `doAuth` 串行执行：第二个请求总是在第一个**完全结束**（绑定成功或回滚）
之后才开始，不会出现两个 `doAuth` 交错。是否顶号取决于新连接是否仍然存活：

| 场景 | 执行路径 | 结果 |
| --- | --- | --- |
| 两个连接都活着（双开/另一台设备） | 第二个拿到锁 → `u.fd=0` → `BindUser` 的 sign 校验通过 → gate 关旧 fd、绑定新 fd → `User.Login` 触发旧会话的 Offline 钩子 | **顶号**，第一个客户端被踢，第二个在线（预期语义） |
| 第二个连接在 auth 完成前已断开 | `BindUser` 第一步 `auth_watch[fd] ~= sign` 即返回 false，**不会执行 `socket.close(old.fd)`**；`doAuth` 再用 `Gate.IsBound` 检查并恢复旧会话 | 第一个会话不受影响，第二个请求静默失败 |
| 同一 fd 连发两个 `C2SLogin` | `auth_watch[fd]` 已被第二个包的 sign 覆盖，第一个的 `BindUser` 校验失败回滚；第二个随后正常绑定 | 不踢人（本来就是同一连接），最终一个会话 |
| 旧会话已 close、`Disconnect` 尚未处理 | 第二个拿到锁时 `u.fd` 仍指向旧 fd；`BindUser` 时 gate 的 `uid_map` 可能已清空；之后迟到的 `Disconnect(uid, fd_A)` 因 `u.fd=fd_B` 被忽略 | 第二个正常上线，无过期事件干扰 |
| `pull=true` | 走 `req.pull` 分支，不碰 fd 与绑定 | 不顶号 |

第二个请求不会重新 `User.Load`：第一个结束后 `uid_map[uid]` 已存在，只走
`BindUser + User.Login` 两次 RPC。

若产品上希望"并发登录时直接拒绝第二个"而不是"后到者顶号"，可把 `lock_uid` 改为
"锁被占用即返回登录繁忙并关闭连接"；本方案选择排队 + 后到者赢，是为了同时兼容
断线重连和正常顶号。

## 5. 详细设计

### 5.1 auth：uid 级 FIFO 锁

```lua
-- Auth.lua
local uid_locks = {}

local function lock_uid(uid)
    local l = uid_locks[uid]
    if not l then
        l = { locked = false, waiters = {} }
        uid_locks[uid] = l
    end
    if not l.locked then
        l.locked = true
        return l
    end
    l.waiters[#l.waiters + 1] = coroutine.running()
    moon.wait()                 -- 挂起，等待锁 owner 移交
    return l                    -- 被唤醒时 locked 仍为 true，所有权已移交
end

local function unlock_uid(l)
    local co = table.remove(l.waiters, 1)
    if co then
        moon.wakeup(co)         -- 直接交给下一个等待者，不经过 unlocked 状态
    else
        l.locked = false
    end
end
```

说明：

- `moon.wait()` 无参挂起，`moon.wakeup(co)` 恢复，返回值为 `BREAK`，不使用；
- 所有权直接移交，避免"解锁后又被新请求抢走"导致等待者饥饿；
- 若 coroutine 在临界区内抛错，由外层 `xpcall` 保证仍然 `unlock`；
- 若登录中被 `moon.quit()` 关闭协程，只发生在关服，锁状态无意义。

### 5.2 auth：`C2SLogin` 改造

```lua
--- 登录失败后的清理，必须在 uid 锁内调用
local function cleanupLogin(req)
    if req.pull then return end
    local u = context.uid_map[req.uid]
    if not u then return end

    if req.fd and req.fd > 0 and u.fd == req.fd then
        --- 已经绑定后出错：解绑并让 user 服务回到离线
        u.online, u.fd = false, 0
        context.GetUserEvent(u.addr_user).User.Logout()
        context.GateEvent.Gate.Kick(req.uid, req.fd)
    elseif u.old_fd then
        --- 异常发生在 BindUser 之前/期间：尽量恢复旧会话
        local old_fd, old_online = u.old_fd, u.old_online
        u.old_fd, u.old_online = nil, nil
        if context.GateRpc.Gate.IsBound(req.uid, old_fd) then
            u.fd, u.online = old_fd, old_online
        end
    end
end

function Auth.C2SLogin(req)
    if not req then return false end

    if not req.pull then
        if not req.openid or #req.openid == 0 then
            kick(req, "openid empty")
            return false
        end
        local ok, uid = xpcall(function()
            return Database.getorcreateuid(context.addr_db, req.openid)
        end, traceback)
        if not ok or not uid then
            kick(req, "get uid failed")
            moon.error("getuid failed", uid)
            return false
        end
        req.uid = uid
    else
        req.openid = ""
        if not req.uid or req.uid == 0 then
            return false
        end
    end

    local l = lock_uid(req.uid)         -- 同一 uid 串行；不同 uid 互不影响
    local ok, res = xpcall(doAuth, traceback, req)

    --- doAuth 成功返回 true，失败返回错误信息。
    --- 错误清理必须在仍持有锁时完成：cleanupLogin 内部会 yield
    --- （User.Logout / Gate.IsBound），若先 unlock，同一 uid 的下一次登录
    --- 可能在这个间隙完成绑定，再被这里恢复的旧会话状态覆盖。
    if not ok or res ~= true then
        local ok2, err2 = xpcall(cleanupLogin, traceback, req)
        if not ok2 then
            moon.error("Auth.C2SLogin cleanup error", err2)
        end
    end
    unlock_uid(l)

    if not ok or res ~= true then
        moon.error("Auth.C2SLogin error", res)
        return false
    end
    return true
end
```

与现状的差别：

- Redis 查询从 `getuidbyopenid + createuid` 改为一次原子的 `getorcreateuid`；
- 整个 `doAuth` 在任何 uid 的登录进行中时不会并发执行；
- `old.online` 判断不再出现在 `C2SLogin` 中，顶号逻辑收进 `doAuth`。

### 5.3 auth：`doAuth` 改造

```lua
local function doAuth(req)
    local u = context.uid_map[req.uid]
    local addr_user

    if not u then
        --- 锁内创建，杜绝并发建出第二个 user 服务
        addr_user = moon.new_service({
            name = "user" .. req.uid,
            file = "game/service_user.lua",
        })
        if addr_user == 0 then
            return "create user service failed!"
        end

        local ok, err = context.GetUserRpc(addr_user).User.Load(req)
        if not ok then
            kick(req, err)
            moon.kill(addr_user)
            return err
        end

        u = {
            addr_user = addr_user,
            openid = req.openid,
            uid = req.uid,
            logouttime = moon.time(),
            online = false,
            fd = 0,
        }
        context.uid_map[req.uid] = u
    end

    --- 离线加载（供其它服务 send_user/call_user 使用），不涉及连接
    if req.pull then
        local openid = context.GetUserRpc(u.addr_user).User.Login(req)
        if not openid then
            kick(req, "pull login failed")
            return "pull login failed"
        end
        return true
    end

    --- 顶号：auth 侧先让旧会话失效。
    --- 这一步之后到达的旧连接 Disconnect 都会因 fd 不匹配被丢弃。
    --- old_fd/old_online 暂存，用于 BindUser 失败或异常时恢复旧会话。
    local old_fd, was_online = u.fd or 0, u.online
    u.old_fd, u.old_online = old_fd, was_online
    u.fd, u.online = 0, false

    --- gate 原子完成：校验 auth_watch → 踢旧 fd → 绑定新 fd。
    --- 改为 RPC 以便拿到成功与否；失败说明新连接在 auth 完成前已断开。
    local ok = context.GateRpc.Gate.BindUser(req.fd, req.sign, req.uid, u.addr_user)
    if not ok then
        --- 若旧连接仍然有效则恢复（见 7.3 的边界说明）
        if old_fd ~= 0 and context.GateRpc.Gate.IsBound(req.uid, old_fd) then
            u.fd, u.online = old_fd, was_online
        end
        u.old_fd, u.old_online = nil, nil
        return "client closed before bind!"
    end

    u.old_fd, u.old_online = nil, nil
    u.fd, u.online = req.fd, true

    --- 不再额外发 User.Logout：
    --- User.Login 内部会先对旧在线状态执行 Offline 钩子（User.lua:73-75），
    --- 且 Login 与钩子在同一 RPC 内，天然有序。
    local openid, name = context.GetUserRpc(u.addr_user).User.Login(req)
    if not openid then
        u.fd, u.online = 0, false
        context.GetUserEvent(u.addr_user).User.Logout()
        context.GateEvent.Gate.Kick(req.uid, req.fd)
        return name
    end

    --- 登录 RPC 期间新连接断开：Disconnect 已排在 Login 之后把 user 服务置离线
    if u.fd ~= req.fd then
        return true
    end

    u.openid, u.name, u.logouttime = openid, name, 0
    context.S2C(req.uid, CmdCode.S2CLogin, {
        ok = true,
        uid = req.uid,
        time = moon.now(),
        timezone = moon.timezone,
        name = name,
    })
    print("login success", req.uid, openid, name)
    return true
end
```

关键点：

1. `u.fd = 0` 发生在 **任何会 yield 的操作之前**（`BindUser` RPC、`User.Login` RPC），
   所以旧连接的 close 事件无论何时被 auth 处理，都不会命中当前会话。
2. `BindUser` 在 `User.Login` 之前：先确认新连接仍然有效，再踢旧连接，
   避免"一个已经死掉的登录请求把在线玩家踢下线"。
3. 删除原来"顶号分支里显式 `User.Logout`"的逻辑（`Auth.lua:126`），
   下线钩子统一由 `User.Login` 触发。
4. 登录失败不再 `moon.kill` 已存在的 user 服务（原 `Auth.lua:59` 在复用服务时也会 kill）。

### 5.4 `Disconnect` 带 fd

```lua
function Auth.Disconnect(uid, fd)
    local u = context.uid_map[uid]
    if not u then return end

    if fd ~= nil and u.fd ~= fd then
        --- 旧连接 / 过期事件，忽略
        return
    end

    u.online, u.fd = false, 0
    u.logouttime = moon.time()
    context.GetUserEvent(u.addr_user).User.Logout()
end
```

### 5.5 gate：`BindUser` 改为 RPC + 原子替换

```lua
--- 返回 true 表示绑定成功；false 表示该 fd 已断开或被新的登录包覆盖
function Gate.BindUser(fd, sign, uid, addr_user)
    if context.auth_watch[fd] ~= sign then
        return false, "client closed before auth done!"
    end

    local old = context.uid_map[uid]
    if old and old.fd ~= fd then
        --- 只关连接；fd_map 交给 close 事件清理，
        --- 避免旧 fd 在途消息因 fd_map 为空被当成登录包
        socket.close(old.fd)
        print("kick user", uid, "oldfd", old.fd, "newfd", fd)
    end

    local c = { uid = uid, fd = fd, addr_user = addr_user }
    context.fd_map[fd] = c
    context.uid_map[uid] = c
    context.auth_watch[fd] = nil
    print(string.format("BindUser fd:%d uid:%d", fd, uid))
    return true
end

--- 供 auth 校验旧会话是否仍然有效
function Gate.IsBound(uid, fd)
    local c = context.uid_map[uid]
    return c ~= nil and c.fd == fd
end
```

注意：

- `Gate.BindUser` 现在通过 `moon.call` 调用，返回值会被 `setup.lua` 的 lua dispatch 打包回传
  （`setup.lua:282-296`），auth 可以感知失败；`Gate.BindUser` 本身在 gate 内同步执行，不阻塞。
- 踢旧连接时**不再** `context.fd_map[old.fd] = nil`。旧 fd 仍留在 `fd_map` 中，
  其迟到的消息会被转发给同一个 user 服务（顶号前的合法操作），不会被误判为登录包。
- 旧 fd 的 close 事件到来时，`on_close` 负责清 `fd_map`。

`Kick` 增加显式 fd，保留 uid 形式兼容旧调用：

```lua
function Gate.Kick(uid, fd)
    if fd and fd > 0 then
        socket.close(fd)
        return true
    end
    local c = uid and uid > 0 and context.uid_map[uid] or nil
    if c then
        socket.close(c.fd)
    end
    return true
end
```

### 5.6 gate：可靠 sign 与关闭处理

```lua
-- 首包：用 gate 内自增序号作为登录凭据，替代 tostring(msg)
context.login_seq = (context.login_seq or 0) + 1
local sign = context.login_seq
context.auth_watch[fd] = sign
...
req.sign = sign
```

原实现用 `tostring(msg)`（Lua 侧收到的是消息对象指针，见 `lua_service.cpp:214-220`），
而消息在队列中回收复用，地址会重复出现，导致"同一 fd 发了第二个包"无法被稳定检测。

`on_close`：

```lua
local function on_close(fd, msg)
    local data = moon.decode(msg, "Z")
    context.auth_watch[fd] = nil

    local c = context.fd_map[fd]
    if not c then
        print("GATE: close", fd, data)
        return
    end

    context.fd_map[fd] = nil
    --- 只有当前绑定仍是这条连接时才清 uid_map
    if context.uid_map[c.uid] == c then
        context.uid_map[c.uid] = nil
    end
    context.AuthEvent.Auth.Disconnect(c.uid, fd)
    print("GATE: close", fd, c.uid, data)
end
```

### 5.7 Database：原子分配 uid

```lua
--- openid -> uid，首次登录时原子创建
function M.getorcreateuid(addr_db, openid)
    local res = call(addr_db, "hget", M.KEY_OPENID, openid)
    if res then
        return math.tointeger(res)
    end

    local uid = math.tointeger(call(addr_db, "incr", M.KEY_UID_SEQ))
    --- HSETNX 成功者获得该 uid；失败说明并发者已写入
    if call(addr_db, "hsetnx", M.KEY_OPENID, openid, uid) == 1 then
        return uid
    end
    return math.tointeger(call(addr_db, "hget", M.KEY_OPENID, openid))
end
```

说明：并发失败时会浪费一个 uid 序号，不影响正确性；保留原 `getuidbyopenid/createuid`
以便其它代码继续使用。

## 6. 错误与边界处理

| 场景 | 处理 |
| --- | --- |
| Redis 查询失败 | `xpcall` 包裹，关闭该连接，不写 `uid_map` |
| `User.Load` 失败 | 踢连接、`moon.kill` 新建服务、不写 `uid_map` |
| `BindUser` 失败（客户端已断） | 恢复旧会话（经 `Gate.IsBound` 校验），返回错误；不踢任何在线连接 |
| `User.Login` 返回失败 | 解绑、踢 fd、置离线；不 kill 已存在的服务 |
| `User.Login` 期间新连接断开 | `Disconnect` 已把 `u.fd` 置 0 并让 user 服务离线；`doAuth` 检测到 `u.fd ~= req.fd`，不再下发 `S2CLogin` |
| 同一 fd 连发两个 `C2SLogin` | 第一个的 `auth_watch` 已被第二个覆盖，`BindUser` 失败回滚；第二个在锁释放后正常绑定 |
| 顶号后旧 fd 的迟到消息 | `fd_map` 仍存在，按普通 C2S 转发给同一 user 服务；不会触发登录 |
| 关服时仍有登录在途 | 该 coroutine 被 `moon.quit` 关闭；已创建但未进 `uid_map` 的服务不会被 `Auth.Shutdown` 调用 `Exit`（见 8.3） |

## 7. 不在本方案内（后续迭代）

### 7.1 旧连接在途 C2S 串入新会话

顶号前旧连接已发出、尚未被 user 服务处理的指令，仍会在新会话中执行。
彻底解决需要在转发帧（`service_gate.lua:45` 的 `redirect`）里携带 `conn_gen`，
user 服务在 `Login` 时记录当前 `conn_gen`，处理 C2S 时丢弃不匹配的帧。
需要改转发参数和 user 服务的 dispatch，约 50 行，建议二期做。

### 7.2 S2C 跨会话投递

S2C 目前只按 uid 路由（`service_gate.lua:80-100`）。旧会话请求的响应可能写到新连接。
由于当前响应大多是可重复的玩家数据推送，影响有限；若要做，需要 S2C 帧携带 `conn_gen`，
属于协议改动，二期评估。

### 7.3 `Gate.IsBound` 的竞态窗口

`BindUser` 失败后恢复旧会话依赖一次 `IsBound` RPC，与旧连接真正关闭之间存在极小窗口
（旧连接在两次 RPC 之间断开）。若发生，auth 会短暂认为旧会话在线，
下一次登录或该 fd 的后续事件会自行纠正。可接受；若要求绝对精确，
可把"校验 + 踢旧 + 绑定"和"恢复"都放到 gate 的一个幂等操作里（`BindUserOrKeep`）。

## 8. 注意事项与已知取舍

### 8.1 为什么不用 `unique = true` 作为主修复

`moon.new_service({ unique = true })` 在服务初始化末尾做 CAS 注册
（`src/moon/services/lua_service.cpp:153-156`），注册失败的服务初始化失败，
创建者拿到的返回值是 0（`src/moon/core/worker.cpp:138-149`）。它能做到和做不到的事情如下。

**能解决：**

- 同一 uid 并发创建时只有一个 `user<uid>` 注册成功，不会出现两个活着的服务
  —— 即 P0-2 中"两份内存数据互相覆盖"的数据后果；
- `moon.queryservice("user"..uid)` 可用，便于失败方复用赢家的服务。

**不能解决：**

- P0-1 顶号时序：旧连接 close → `Disconnect(uid)` 仍是按 uid 生效，`unique` 管不到；
- 失败方没有出口：`doAuth` 拿到 0 目前直接返回失败（`Auth.lua:41-43`），
  第二个登录会失败并占着 `auth_watch` 直到超时；要复用赢家的服务，
  还得等赢家的 `User.Load` 完成，需要额外的 ready 握手；
- 胜负由 CAS 完成顺序决定，不是"最后登录者赢"；
- P1-1 假在线、P1-2 sign、P1-3 uid 分裂、P2 在途消息，全部不受影响。

**当前版本的两个硬坑：**

1. `unique_services_` 只有 `set_unique_service` / `get_unique_service`，
   **全项目没有任何删除逻辑**（`src/moon/core/server.cpp:252-266`），
   `worker::remove_service`（`worker.cpp:164-208`）销毁服务时也不清理。
   而 `Auth.lua:48、59` 在 `Load/Login` 失败时会 `moon.kill(addr_user)` ——
   一旦开启 `unique`，这次 kill 会让 `user<uid>` 这个**名字永久被占用**，
   该玩家之后每次登录都返回 0，再也登不上。
2. `unique` 只在一个进程内有效，多节点部署时不是全局唯一；本方案的单节点场景勉强可用，
   但它仍然不能替代会话层的串行化。

**如果坚持使用，需要同时满足：**

1. 修改 C++：服务销毁时移除 unique 注册项，或彻底去掉运行期的 kill 路径；
2. auth 增加"创建失败 → `queryservice` 找到赢家 → 等其 Load 完成再复用"的握手，
   或直接返回"登录繁忙"让客户端重试；
3. 顶号顺序、过期 `Disconnect` 仍需单独处理。

因此本方案以 auth 侧 uid 锁作为唯一性保证，`unique` 只作为修好注册表清理后的第二道保险。

### 8.2 登录串行化的代价

同一 uid 的第二个登录会等待第一个完成（正常情况下是毫秒级：一次 Redis 读 + 一次 RPC）。
若 Redis 异常超时，第二个登录也会一起等待。当前未加锁超时；
如需要，可增加 `moon.timeout` 唤醒并在超时后返回"登录繁忙"，但必须保证锁的释放。

### 8.3 关服流程

`Auth.Shutdown` 只遍历 `uid_map` 调 `User.Exit`。本方案消除了重复服务，
但"登录在途、尚未写入 `uid_map`"的服务仍不会被 Exit。
可在 auth 记录 `pending_services`（创建后、写入 `uid_map` 前登记，写入后移除），
`Auth.Shutdown` 一并 Exit。属于低优先级健壮性改进。

### 8.4 user 服务不回收

现状是玩家下线后服务常驻，登录过的人数越多内存越高。本方案不改变这一点。
若后续要回收，必须先解决 8.1 的 unique 名字泄漏，或由 auth 用 `uid_map` 自行登记地址。
