# 游戏服务器协议定义与编解码方案

> 适用范围：本项目（MoonFarm）以及一般的 Lua/C++ 游戏服务端。
> 当前项目的具体协议表见 [design.md §3](design.md#3-协议)；本文讲的是**选型思路与工程实践**。

---

## 1. 先分层：协议不是一层

很多讨论之所以混乱，是因为把不同层的东西放在一起比较。实际上一套网络协议可以拆成六层，**每层都能独立选型**：

```
┌─ 定义层 ────────── IDL(.proto) / 无 schema / 手写布局 / 配置表
├─ 编解码层 ──────── JSON / protobuf / MessagePack / 自定义二进制
├─ 压缩加密层 ────── deflate / zstd / lz4 / AES / 自定义混淆
├─ 分发层 ────────── 消息码(CmdCode) / 路由到 handler
├─ 分帧层 ────────── 长度前缀 / 分隔符 / WebSocket 帧 / 固定包长
└─ 传输层 ────────── TCP / UDP / KCP / WebSocket / HTTP2 / QUIC
```

例如"protobuf over WebSocket + deflate"与"JSON over TCP"只在编解码层不同，传输层可以完全一样。

**常见误区**：把"用了 protobuf"等同于"性能好"。如果分帧设计糟糕（比如每条消息都新开连接），编解码再快也没有意义。

## 2. 协议定义方式：五种主流路线

### 2.1 IDL + 编译期代码生成

```
xxx.proto --protoc--> xxx.pb.h/.cc (C++)、xxx_pb.js (JS)、Xxx.cs (C#)
```

- **代表**：protobuf、FlatBuffers、Cap'n Proto、Thrift
- **优点**：类型安全、跨语言一致、性能好、字段号即 API 约定
- **缺点**：需要构建链路；客户端/服务端生成物必须同步；热更不友好
- **适用**：C++/C#/Java/Go 等强类型客户端与服务端

### 2.2 IDL + 运行期反射

```
xxx.proto 文本 --protoc.lua--> 描述符 --pb.load--> 内存类型表
消息字节 --pb.decode("MsgName", bytes)--> Lua table
```

- **代表**：本项目使用的 `protoc.lua + pb`、JS 的 protobufjs、Python 动态 API
- **优点**：无需构建流程、schema 可运行时加载、对热更友好
- **缺点**：启动时有解析成本、类型错误暴露较晚、每次编解码都要查表
- **适用**：Lua/JS 这类没有编译期的服务端

### 2.3 无 schema · 自描述格式

- **代表**：JSON、MessagePack、CBOR
- **优点**：零工具链、可读、字段可随意增删、调试极其方便
- **缺点**：体积大、无类型校验、字段名拼错会静默失败
- **适用**：低频业务消息、Web/H5、运营后台、内部服务

### 2.4 手写二进制布局（C struct 风格）

```c
struct PlotData {
    int32_t index;
    int32_t state;
    int64_t planted_at;
    // ...
};  // #pragma pack 或手动按字节布局，收发直接 memcpy
```

- **优点**：极致性能、代码直观、几乎没有解析开销
- **缺点**：**没有兼容性**——加字段或改顺序就全崩；跨语言要对齐；需约定大小端
- **适用**：战斗同步、高频小包、客户端与服务端同版本发布的项目

### 2.5 配置表驱动（静态数据）

Excel/CSV → 导表工具 → 二进制或代码。这不是网络协议方案，但常被混为一谈；**动态消息不要用导表**。

## 3. 编码格式对比

| 格式 | 体积 | 编码速度 | 解码速度 | 可读性 | Schema | 零拷贝读 | 跨语言 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| JSON | 大（基准 1.0） | 中 | 中 | ★★★★★ | 无 | 否 | ★★★★★ |
| MessagePack | 中（0.5~0.7） | 快 | 快 | ★★（需工具） | 无 | 否 | ★★★★ |
| protobuf | 小（0.25~0.4） | 快 | 快 | ★（需 schema） | 有 | 否 | ★★★★★ |
| FlatBuffers | 小~中 | 快 | 极快 | ★ | 有 | **是** | ★★★★ |
| Cap'n Proto | 小~中 | 快 | 极快 | ★ | 有 | **是** | ★★★ |
| 自定义二进制 | 最小 | 最快 | 最快 | 无 | 手写 | 可 | ★★ |
| 文本（HTTP/Redis） | 大 | 慢 | 慢 | ★★★★★ | 无 | 否 | ★★★★★ |

**几个关键判断：**

- **FlatBuffers / Cap'n Proto 的卖点是"读取不反序列化"**：直接从缓冲区按偏移取字段。适合超大对象、移动端、频繁随机访问；代价是写入需要"构建"，二进制结构也更复杂。
- **MessagePack 是"二进制 JSON"**：字段名照传，只是编码更紧凑。适合想省带宽但不想维护 IDL 的场景。
- **protobuf 的优势在"通用"**：体积、速度、生态、跨语言都比较均衡，没有明显短板。
- **自定义二进制只在"极度可控"时划算**：同一团队、客户端服务端同版本、协议稳定。

## 4. 实际游戏的组合方式

几乎没有项目只使用单一方案：

| 模块 | 常见选择 | 原因 |
| --- | --- | --- |
| 登录 / 账号 / 支付 | HTTP + JSON | 需对接第三方、可读、易排错 |
| 大厅 / 匹配 / 商城 / 邮件 | JSON 或 MessagePack | 低频、字段多变 |
| 战斗 / 房间同步 | protobuf 或自定义二进制 | 高频、小包、延迟敏感 |
| 弱网实时（MOBA/FPS） | UDP/KCP + 二进制 + 压缩 | 需要可控的丢包重传 |
| 聊天 / 社交 | JSON，可加压缩 | 文本为主，量大但可容忍延迟 |
| GM / 运维 / 监控 | JSON | 人工可读 |
| 状态同步 | 增量 + 二进制 + 序号 | 只传变化，可回滚 |

大厂项目里"两套甚至三套协议并存"是常态，不是设计缺陷。

## 5. 工程化关键点

选型只是起点，下面这些决定项目能不能安稳运营。

### 5.1 单一事实来源

`.proto`（或一份协议描述文件）必须是唯一源头，以下内容应当**自动生成**：

- 服务端消息码表（当前 `server/common/CmdCode.lua` 为手写，依赖注释提醒同步）
- 客户端协议代码 / 内嵌 schema（`tools/gen_proto_inline.js` 的产物）
- 协议文档

手工同步是最大的长期隐患。

### 5.2 消息码管理

- **永不复用已删除的消息码**（旧客户端可能仍在发送）
- 删除时留空洞，或显式标记 `reserved`
- 预留号段给不同模块（如 1~99 系统、100~199 农场、200~299 社交）
- 上线前冻结，变更通过版本号管理

### 5.3 兼容性规则（以 protobuf 为例）

**允许：**

- 新增字段（使用新的字段号）
- 新增消息
- 删除字段时把字段号标记为 `reserved`

**禁止：**

- 修改已有字段的字段号
- 修改已有字段的类型（`int32` → `string`）
- 复用已删除的字段号

原则：**只增不改**。客户端需要能同时兼容服务端 N 和 N-1 两个版本。

### 5.4 版本协商

登录时交换：

- 协议版本号 / schema hash
- 客户端版本号

不匹配时：提示更新 / 兼容降级 / 拒绝连接。没有版本协商，线上协议一变就是"莫名其妙全挂"。

### 5.5 校验与安全

- **长度上限**：单帧（如 64KB）超限直接断开
- **嵌套深度上限**：防止恶意深嵌套导致栈溢出
- **消息码白名单**：未知 cmd 直接拒绝，不进入业务层
- **`pcall` 包住解码**：解码失败断开连接，避免异常扩散
- **不信任客户端字段值**：索引越界、数量为负、类型不符都要校验
- **限流**：同一连接每秒消息数上限

### 5.6 数字精度

- JS 的 `number` 是 double，精确整数上限为 **2^53**
- 大整数（雪花 ID、高倍时间戳）一律**用字符串传输**
- 金额使用整数（分），**不要用 float**
- 浮点只用于展示类数据（进度、坐标），并约定精度

### 5.7 性能

- **零拷贝**：能传 buffer 指针就不要先转成 Lua 字符串
  （本项目 `pb.decode(name, ptr, len)` 正是直接读 buffer 内存）
- **复用缓冲**：编码时复用 buffer，避免每帧新建
- **减少临时表**：高频协议可考虑对象池
- **关注 GC**：Lua 的 table 分配是主要开销
- **压测要分离**：把编解码耗时、业务耗时、网络耗时分开统计

### 5.8 压缩

- 按连接协商（WebSocket 的 `permessage-deflate`），或在应用层按阈值压缩
- 小包（< 200B）通常不值得压缩（压缩头本身就有开销）
- zstd / lz4 比 deflate 更快，但需考虑客户端支持
- 压缩是 CPU 换带宽，移动端尤其要算电池账

### 5.9 调试能力

- **hex dump 工具 + schema**：能把抓包结果还原成可读结构
- **双协议**：debug 通道允许 JSON，正式通道走二进制
- **日志采样**：高频消息不要全量打印
- **录制回放**：把客户端消息序列录下来，方便复现问题

### 5.10 Schema 共享与热更

- 服务端多 VM（moon 中每个 service 一个 `lua_State`）共享一份 schema：`pb.share_state()`
- **schema 热更风险高**：已解码的数据结构变了、旧连接仍在使用旧格式
- 常规做法：**业务代码可热更，消息结构变更走重启/版本切换**

### 5.11 多语言一致性

- 生成物纳入版本库
- CI 校验"proto 改了但生成代码未更新"的情况直接失败
- 客户端内嵌 schema 时带 hash 做校验

### 5.12 测试

- **Round-trip**：编码 → 解码 → 与原表一致
- **兼容性**：新代码解旧数据、旧代码解新数据
- **Fuzz**：随机字节喂给解码器，不允许崩溃
- **端到端**：真实客户端跑完整流程（本项目已有 `tools/test_e2e.js`）

## 6. 本项目现状对照

| 层 | 现状 | 评价 |
| --- | --- | --- |
| 定义 | `.proto` + `protoc.lua`（启动时）+ `pb` | 合理，动态语言的典型做法 |
| 分发 | 手写 `CmdCode.lua` + 2 字节 cmd + uid 前缀 | **最值得改进**：应自动生成 |
| 编码 | protobuf，buffer 指针零拷贝 | 实现质量不错 |
| 分帧 | `uid(seri) + cmd(u16 LE) + payload` | 简单够用 |
| 存储 | Redis 存整条 JSON | 与网络协议解耦，正确 |
| schema 共享 | `pb.share_state()` | 正确；注意宿主服务生命周期 |
| 版本协商 | 无 | 上线前应补 |
| 校验 | 有 `pcall`，缺长度/白名单/限流 | 建议补 |

### 6.1 编解码调用链（当前）

```
收包：
  C++ socket → PTYPE_C2S → service_user.lua 的 raw_dispatch
    → moon.decode(msg, "B")          [C: message → buffer 指针]
    → protocol.decode(buf)           [Lua]
        → buffer.unpack(buf, "<HC")   [C: 读 2 字节 cmd + payload 指针]
        → pb.decode(name, p, n)       [C: 按 schema 还原 table]
    → command[cmd](data)

发包：
  context.Send(...) → protocol.encode(uid, cmd, t)
    → seri.packs(uid) + cmd + pb.encode(name, t)
    → raw_send('S2C', gate, ...) → gate → socket.write
```

### 6.2 可选替换方案

| 方案 | 改动量 | 风险 | 学习价值 |
| --- | --- | --- | --- |
| 换 JSON | 新增 `protocol_json.lua` + 客户端 | 低 | 高（理解自描述格式） |
| 换 MessagePack | 需引入/实现 msgpack 模块 | 中 | 高 |
| 自定义 TLV | 服务端、客户端各写一份 | 中 | 很高（理解 wire format） |
| 保持 protobuf | 无需改动 | — | 需阅读库源码 |

替换时只需实现 `common/protocol_pb.lua` 的 5 个函数
（`encode` / `encodestring` / `decode` / `decodestring` / `name`），
在 `common/init.lua` 改一行即可切换，C++ 核心无需改动。

## 7. 选型决策清单

按顺序回答以下问题，基本就能定下来：

1. **消息频率？** 每秒 > 10 条 → 二进制；否则 JSON 可接受
2. **单包大小？** 平均 > 1KB 且量大 → 考虑压缩或更紧凑格式
3. **客户端是什么？** Web/JS → JSON 最省事；Unity/UE → protobuf/FlatBuffers
4. **团队几种语言？** ≥ 3 种 → 用有成熟生成器的 IDL（如 protobuf）
5. **协议变更频率？** 高 → JSON/MessagePack；低且稳定 → 自定义二进制
6. **调试成本 vs 带宽成本？** 小项目优先调试体验
7. **是否需要零拷贝随机访问？** 是 → FlatBuffers/Cap'n Proto
8. **是否需要兼容多个客户端版本？** 是 → 必须选有明确兼容规则的格式（protobuf）

## 8. 一页结论

```
定义层：  .proto（单一来源） + 代码/表自动生成
分发层：  消息码 → handler 表，永不复用，带白名单
编解码：  业务消息 JSON / 高频战斗 protobuf 或自定义二进制
传输层：  TCP / WS（H5），弱网 KCP/UDP
压缩：    按连接协商，小包不压
安全：    长度上限 + 深度上限 + pcall + 限流 + 字段校验
版本：    登录交换协议 hash，支持 N/N-1
调试：    hexdump 工具 + debug 通道 JSON
演进：    先保证"单一来源 + 版本协商"，再谈性能优化
```

**协议选型没有银弹。真正的分水岭不是"JSON 还是 protobuf"，而是是否做到：**

1. 定义单一来源
2. 兼容规则明确
3. 错误可观测

这三件事做到位，用哪种格式都能上线；做不到，用 protobuf 也照样出事故。
